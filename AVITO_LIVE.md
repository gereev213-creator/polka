# avito_live вместо старого сборщика

## Что заменено
- Ссылочные поиски («Мои поиски» из ссылки Авито) опрашивает `avito_live`.
  Мост в `polka_bot-9-3.py` (`_live_link_sync_loop`) раз в 30 с сверяет активные
  `hunt_criteria` со слежениями: новый поиск → слежение, пауза/удаление/конец
  пробного периода → слежение выключается, смена тарифа → меняется частота
  (`_link_check_min`: 1 мин платным, 5 мин бесплатным).
- Старый сборщик удалён: `collector/`, циклы `_collector_*`, HTTP-приём
  находок и GitHub Actions. Секреты и конфиг заархивированы вне git.
- Граница цены из поиска применяется к находкам (Авито теряет `pmax` при копировании ссылки).
- `/watch`, `/watches`, `/unwatch` работают как раньше (отдельно от поисков бота).

## Откуда берутся объявления (важно)
- `window.__initialData__` Авито больше не отдаёт. Парсер читает JSON состояния
  страницы: `<script type="mime/invalid" data-mfe-state="true">` →
  `loaderData.data.catalog.items`.
- Там лежит **только основная выдача**. «Похожие» — в `extraBlockItems`, они не
  берутся (из-за них старый сборщик присылал чужие лоты и чужие регионы).
- Время публикации — `sortTimeStamp` (в миллисекундах), фото — `images`.
- Запасные пути: старый `__initialData__`, затем микроразметка `data-marker="item"`
  с отсечкой блока `extra-` (проверено: 8 карточек основной выдачи из 50 в разметке).

## Что поправлено при проверке 21.11.2026
- **Источник данных** — `data-mfe-state`. Без этого парсер не находил ни одной
  карточки: страница отдаётся с 200, но `__initialData__` в ней нет.
- **Профиль по умолчанию `edge101`**: `chrome124` Авито стабильно режет 429/403
  (проверено с двух IP: с одного и того же адреса edge101 — 200, chrome124 — 429).
- **Повторы со сменой IP**: `AVITO_TRIES` (по умолчанию 3). Пауза после смены
  берётся из ответа провайдера (`rt`), а не фиксированные 8 с.
- 439/403/429 — блокировка с бэкоффом, а не обычная ошибка.
- Маркеры блокировки ищутся без учёта регистра.
- Пустой поиск («ничего не найдено») считается распознанной страницей, а не сбоем.

## Ограничение: Авито пускает вероятностно
С одним мобильным прокси запрос проходит примерно каждый 3–6-й раз, даже со
сменой IP. Замер 21.11.2026: полный цикл (получить выдачу + baseline + отправка
новой находки) занял ~4 минуты и 13 смен IP.
Поэтому:
- `AVITO_POLL_SEC=20` на одном прокси — нереально; ставьте 120–300.
- Одновременных запросов не больше, чем прокси (`AVITO_CONCURRENCY`).
- Для мониторинга «за секунды», как у конкурентов, нужен либо пул из десятков
  прокси, либо решение PoW (`collector/avito_api`, в бота пока не подключено).

## Переменные в Amvera
| Переменная | Значение |
|---|---|
| `AVITO_PROXIES` | `socks5h://логин:пароль@bproxy.site:11542` (несколько — через запятую) |
| `AVITO_PROXY_ROTATE_URL` | `https://changeip.mobileproxy.space/?proxy_key=…&format=json` |
| `AVITO_TRIES` | 3–6 |
| `AVITO_IMPERSONATE` | `edge101` |
| `AVITO_CONCURRENCY` | 1–2 (по числу прокси) |
| `AVITO_POLL_SEC` | 120–300 |
| `ADMIN_IDS` | уже есть — туда придёт предупреждение о блокировках |

`/health` показывает блок `avito_live`: `links`, `proxies`, `blocked_links`.

## Перед деплоем
1. `python3 check_avito_proxy.py "<ваша ссылка Авито>"` с `AVITO_PROXIES` и
   `AVITO_PROXY_ROTATE_URL`.
2. `python3 test_avito_live.py` — 18 проверок.
3. `python3 live_smoke.py "<ваша ссылка>"` — полный цикл на живой странице.
4. Деплой как обычно: `git add -A && git commit && git push amvera master`.

## Куда уходят находки
Находка avito_live идёт в общий конвейер находок (`ingest_findings`), а не
отправляется напрямую: `hunt_matches` → сообщение в Telegram и лента
«Находки» в Mini App. Тот же путь, которым раньше шли находки старого
сборщика. Ручные `/watch` (без критерия бота) отправляются напрямую.
